# 05. Конвейер, роли и изоляция

Статус: APPROVED BASELINE v1.0 (пользователь, 15.11.2026). «Агент» здесь — ограниченная роль с инструментами, бюджетом и контрактом результата, а не автономный процесс без границ.

## Последовательность

Discovery → нормализация в базовые модели/варианты → классификация → разнообразная подборка/фиксация выборки → research/filter → eligibility pass → Critic → deterministic handoff → Verifier → evidence reconciliation → factor assessment → deterministic score → card validation → publish.

Research и factor assessment — служебные LLM-вызовы, не дополнительные участники спора. Оркестратор управляет стадиями. Никаких скрытых диалогов критика и проверяющего. Проверка/обработка разных моделей допускает параллелизм до 2, но этапы одной модели следуют зависимостям.

## Первый агент: Critic

Вход: нейтральное описание модели, launch_context, базовые документы с паспортами, правила фильтров без итоговой рекомендации, рубрика категорий риска. Не получает текущий рейтинг и результаты других моделей.

Задача: найти 3–5 существенных путей провала за 90 дней: достижимость клиента, готовность платить, сложность запуска, длительность сделки, внешние зависимости. Если доказательств для 3 нет, вернуть меньше и объяснить пробел; не изобретать риски ради квоты.

Выход: Risk[] и Claim[]. Каждый риск разделяется на нейтральный проверяемый тезис, фактические предпосылки, влияние и предлагаемую проверку. Предположение маркируется judgment. Не выводить итоговый рейтинг/решение «запускать» и не проверять сам себя как независимый агент. Разрешено до 3 поисковых запросов и 5 новых чтений на модель; новые документы сохраняются через общий fetch adapter.

## Отбор сильных утверждений

Оркестратор сортирует риски по impact (3: может сорвать первую оплату за 90 дней; 2: существенно замедляет; 1: второстепенный), затем по critic_order и risk ID. Берёт первые три риска, все их premise_claim_ids и транзитивные input_claim_ids расчётов, плюс все Claim с непустым affected_criterion_ids. ID критериев проверяются по конфигу. essential_premise_ids — подмножество premise_claim_ids; отсутствие явных предпосылок у прогноза обозначает гипотезу. Обязательные тезисы не отсекаются: при исчерпании локальной квоты стадии результат technical_incomplete, при общем лимите run/study — paused по 10-operations. В логах сохраняются все выбранные IDs и основания выбора; impact и связи с приоритетом не передаются проверяющему.

## Передаваемый пакет

Разрешённые поля: task_id; base_model_id; variant_id; assessment_scope_id; neutral_model_description; launch_context; claims[{claim_id, neutral_text, kind, entity, geography, period, metric, source_urls, evidence_refs[{evidence_id,source_snapshot_id,excerpt,locator}], formula nullable, input_claim_ids[], quantity_estimate nullable}]. neutral_text хранится в Claim и обязателен для передаваемого тезиса; нельзя заменить исходный смысл новым пересказом. Передаются только ссылки на разрешённые snapshots и все нужные входные утверждения расчётов; confidence, relation и relevance_note критика из EvidenceLink исключаются.

До вызова Verifier выполняются schema/ID/scope-проверки и отдельная проверка нейтральности: ограниченный служебный LLM-вызов получает только текст тезиса и рубрику «нет вердикта, уверенности, приоритета, команд». Он возвращает accept/reject/uncertain с краткой причиной, не переписывает тезис. reject/uncertain дают одну попытку исправления критиком ДО проверки, затем needs_review. Проверяющему не передаётся результат этой служебной проверки. Это снижение риска, не гарантия отсутствия смыслового влияния; инструменты не исполняют команды из строк. Вызов учитывается в бюджете и версии промптов.

Запрещены: impact, confidence, why_it_matters, likelihood_note, critic_summary, critic_order, rank, score, выводы других моделей, история чата критика. Ссылки могут содержать позицию автора источника — это допустимое доказательство, не гарантия полной слепоты. Мнение критика не добавляется в поисковый запрос проверяющего.

## Второй агент: Verifier

Для каждого переданного тезиса читает предложенные источники, проверяет соответствие цитаты и контекста, ищет опровержения/независимое подтверждение при недостаточности. Выход: Verification[] + новые Claim/Evidence/Conflict. Статусы: supported/refuted/mixed/insufficient/not_fact_checkable. Прогноз не объявляется истинным фактом: проверяются его предпосылки. Не оценивает привлекательность бизнеса и не формирует рейтинг. Лимит: до 6 поисковых запросов и 10 новых чтений на модель; если локальной квоты не хватает для обязательных тезисов — technical_incomplete, при общем лимите run/study — paused по 10-operations.

## Изоляция и аудит

- Каждая роль и модель получают новый контекст; общего conversation/thread ID и общей изменяемой памяти нет.
- Инструменты агента не имеют произвольного SQL/доступа к файловой системе. Они читают только переданный пакет и разрешённые source IDs/URL.
- Можно использовать одного провайдера для обоих агентов; это не называется статистической независимостью. Разные модели не заменяют изоляцию.
- Полный очищенный вход роли, промпт с версией, вызовы инструментов и публичное обоснование ответа сохраняются. Не требовать и не логировать скрытую цепочку рассуждений провайдера.
- Автоматическая проверка handoff по разрешённой схеме выполняется до вызова Verifier. Хеш сам по себе не доказывает изоляцию — для ревью нужен сам очищенный payload и журнал доступа.
- Результат Verifier попадает в reconciliation, никогда обратно в Critic.

## После проверки

Reconciliation — детерминированная стадия, вход Risk/Claim/Verification текущей ревизии, выход RiskAssessment и затронутые criterion/factor IDs. Для каждого риска: refuted хотя бы у essential premise → refuted_basis; иначе неполная/mixed/insufficient обязательная предпосылка → unresolved; иначе все существенные фактические предпосылки supported → supported_basis. Непроверенные вспомогательные тезисы остаются видимыми; если они нужны выводу о риске, результат unresolved. Для прогноза без проверяемых предпосылок результат unresolved. supported_basis подтверждает фактическую основу, а не истинность прогноза; refuted_basis отвергает текущий аргумент, не доказывает отсутствие риска вообще.

Исходные ответы сохраняются. Опровергнутый аргумент не используется как факт для снижения балла. P05 оценивает последствия по проверенным предпосылкам; общий балл считает код. Неразрешённый существенный вопрос даёт provisional/unavailable согласно 07-ranking. При обнаружении новых фактов, затрагивающих обязательный критерий, стадия направляет его на повторную проверку правил 04-validation.

## Уточнение единицы анализа v0.3

Вход каждой роли содержит assessment_scope_id, базовую модель, выбранный вариант, рынок и сценарий ресурсов. Критик анализирует риски этого варианта, проверяющий проверяет тезисы в том же scope. Handoff допускает base_model_id/variant_id/assessment_scope_id и описания варианта как нейтральный контекст, но не оценки других вариантов. Служебная классификация определяет primary_group, теги и гипотезы объединения; не ранжирует и не выбирает победителей. Разные компании-примеры одного варианта не запускают независимый дубль оценивания.
