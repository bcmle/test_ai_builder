# 05. Конвейер, роли и изоляция

Статус: спецификация с дополнением v1.5.2 по поручению пользователя 16.11.2026; реализация нового контракта не выполнена этим шагом. «Агент» здесь — ограниченная роль с инструментами, бюджетом и контрактом результата, а не автономный процесс без границ.

## Маршрутизация допуска v1.5.2

[15-conditional-scoring](15-conditional-scoring.md) имеет приоритет для допуска и статуса score в новой версии. Роли сохраняют честные criterion results и доказательства; только приложение вычисляет confirmed/conditional/blocked/unresolved. Допущения F01/F03/F05–F07 передаются как `eligibility_conditions[]` с границами сценария и влиянием на сроки/затраты/факторы, не как подтверждённые внешние факты. F02/F04/F08/F09/F10 требуют pass; F09 проверяет самостоятельный коммерческий сервис, а не госзаказчика. F03=unknown после завершённого исследования для явно описанных рынка и нашей роли допускает conditional с проверкой необходимости собственной специальной лицензии до первого клиента. Подтверждённое требование такой лицензии блокирует этот сценарий; существенное противоречие о применимости найденного требования, запрете или конструкции оставляет unresolved. Неописанный/неисследованный сценарий и технический сбой не дают условного допуска. Старый граф, schemas, prompts, snapshots и оплаченные receipts не переводятся на v1.5.2 задним числом; новый run/revision сохраняет происхождение по 03/15.

Перед условным допуском F01/F03 обязательны предварительный поиск и независимая проверка применимости к описанной роли/рынку; сохраняются просмотренные материалы, границы поиска и пробелы. Недостаточность этих оснований может остаться completed unknown. Отсутствие выполнения стадии не маскируется условием; финальная правовая проверка до первого клиента может оставаться открытой по 15.

## Работа с юридическими документами аналогов — v1.5.2

Research выполняет поиск и чтение доступных релевантных Legal/Terms, Privacy, DPA, AUP и лицензионных документов каждого аналога-компании/продукта, используемого в анализе/карточке, включая дополнительные. Состав аналогов фиксируется в manifest; это требование не распространяет исследование на каждую случайно упомянутую в поисковой выдаче компанию. Результат — отдельный `AnalogueLegalReview` по 03 с фактическими действиями поиска, snapshot refs, версиями/датами либо явной неизвестностью, релевантными пунктами, ролями сторон, территорией, потоком денег, ограничениями и применимостью к нашему сценарию.

Выполняется ограниченный поиск в действующем бюджете, а не поиск до обязательного нахождения каждого типа документа. Доступный релевантный текст читается; документы не считаются изученными по заголовку или наличию ссылки. Необнаружение, внешние 404/login/robots/таймауты после предусмотренных попыток либо недостаточность прочитанного фиксируются как completed review с coverage not_found/unavailable/insufficient и конкретными gaps/recheck conditions. Ограничения доступа не обходятся. Coverage reviewed означает изучение доступных релевантных материалов, не подтверждённую законность. Пропуск работы или сбой аналитического этапа не получают completed; при достижении общего лимита действует прежняя пауза по 10, а не выдуманный результат поиска.

Пункты договора подтверждают, что именно заявляет поставщик. Исследователь/P02V/Verifier не выводят из Terms общий lawful pass, не смешивают software license с разрешением регулятора, governing law с доступными рынками или молчание о лицензии с освобождением от неё. Для необходимых вопросов F01/F03 используются адресные официальные проверки; сохраняются допустимые unknown и условный допуск по 15. Само отсутствие юридических документов аналога не блокирует conditional при выполненной работе и остальных выполненных требованиях.

Critic получает документы и явные пробелы как часть разрешённого контекста. P02V/Verifier получают нейтральные тезисы о конкретных пунктах, источники и контекст применимости без вывода исследователя о допуске; полный чужой review не передаётся вместо whitelist. Добавленный позднее аналог тоже требует своего review. Новые документы после замораживания пакета проходят существующую новую ревизию/run и повторную проверку затронутых зависимостей; frozen inputs не дополняются на месте. По canonical URL/snapshot разрешено переиспользовать прочитанный материал с исходным provenance, но не вывод применимости к другому scope без проверки. Лимиты и платные роли не расширяются этим документом.

## Исправление ответа и возобновление — v1.4

Для каждой роли разрешён исходный ответ и максимум две корректировки schema/semantic errors. Коррекция получает только исходный allowlisted пакет этой роли, её собственный неверный ответ и безопасные ошибки валидации. Verifier не получает суждения/оценки Critic даже при repair. Нельзя угадывать ID, заменять доказательства похожими, ослаблять gate или требовать pass. При недостатке основания корректный результат — unknown.

После каждой попытки выполняются все структурные и семантические проверки; только затем создаётся accepted receipt. Старые неверные receipts сохраняются неизменными и отвергаются для дальнейшего продвижения. Детерминированные ключи попыток и сохранённый счётчик обеспечивают replay без новой оплаты исходного ответа или уже выполненной корректировки. После двух неудачных корректировок сохраняется явная техническая остановка. Refusal, auth/quota, budget и неизвестный результат/биллинг запроса не являются ошибками схемы и не запускают repair.

## Последовательность

Discovery → нормализация в базовые модели/варианты → классификация → разнообразная подборка/фиксация выборки → research с AnalogueLegalReview для всех используемых аналогов / filter → deterministic eligibility confirmed/conditional → Critic → deterministic handoff → Verifier → evidence reconciliation → factor assessment → deterministic score candidate → card validation → final/conditional publication.

Blocked завершает маршрут карточкой отклонения; unresolved сохраняет вопрос/техническую причину и не проходит в рейтинг. Разрешённые условия conditional дают проход к дальнейшему исследованию, но не готовый балл. После reconciliation и проверки карточки агрегатор повторно определяет допуск: применимый запрет, подтверждённая обязательная собственная специальная лицензия или несовместимость → blocked; unknown F02/F04/F08/F09/F10 или существенное противоречие → unresolved; допустимые открытые условия F01/F03/F05–F07 → conditional. Финальный либо условный статус score назначается только после успешного завершения всех обязательных проверок и обоснования S01–S05; до этого возможен лишь provisional либо unavailable по 03/07/15.

Research и factor assessment — служебные LLM-вызовы, не дополнительные участники спора. Оркестратор на LangGraph управляет стадиями и условными переходами. Никаких скрытых диалогов критика и проверяющего. Проверка/обработка разных моделей допускает параллелизм до 2, но этапы одной модели следуют зависимостям.

## Первый агент: Critic

Вход: нейтральное описание модели, launch_context, базовые документы с паспортами, правила фильтров без итоговой рекомендации, рубрика категорий риска, явно маркированные условия operating design и непроверенные условия запуска. Не получает текущий рейтинг и результаты других моделей. Critic проверяет, можно ли сохранить предлагаемую ценность/выручку при отказе от кредита, страхового риска и custody; не считает отказ уже подтверждённым фактом о действующем бизнесе.

Задача: найти 3–5 существенных путей провала за 90 дней: достижимость клиента, готовность платить, сложность запуска, длительность сделки, внешние зависимости. Если доказательств для 3 нет, вернуть меньше и объяснить пробел; не изобретать риски ради квоты.

Выход: Risk[] и Claim[]. Каждый риск разделяется на нейтральный проверяемый тезис, фактические предпосылки, влияние и предлагаемую проверку. Предположение маркируется judgment. Не выводить итоговый рейтинг/решение «запускать» и не проверять сам себя как независимый агент. Разрешено до 3 поисковых запросов и 5 новых чтений на модель; новые документы сохраняются через общий fetch adapter.

## Отбор сильных утверждений

Оркестратор сортирует риски по impact (3: может сорвать первую оплату за 90 дней; 2: существенно замедляет; 1: второстепенный), затем по critic_order и risk ID. Берёт первые три риска, все их premise_claim_ids и транзитивные input_claim_ids расчётов, плюс все Claim с непустым affected_criterion_ids. ID критериев проверяются по конфигу. essential_premise_ids — подмножество premise_claim_ids; отсутствие явных предпосылок у прогноза обозначает гипотезу. Обязательные тезисы не отсекаются: при исчерпании локальной квоты стадии результат technical_incomplete, при общем лимите run/study — paused по 10-operations. В логах сохраняются все выбранные IDs и основания выбора; impact и связи с приоритетом не передаются проверяющему.

## Передаваемый пакет

Разрешённые поля: task_id; base_model_id; variant_id; assessment_scope_id; neutral_model_description; launch_context; claims[{claim_id, neutral_text, kind, entity, geography, period, metric, source_urls, evidence_refs[{evidence_id,source_snapshot_id,excerpt,locator}], formula nullable, input_claim_ids[], quantity_estimate nullable}]. neutral_text хранится в Claim и обязателен для передаваемого тезиса; нельзя заменить исходный смысл новым пересказом. Передаются только ссылки на разрешённые snapshots и все нужные входные утверждения расчётов; confidence, relation и relevance_note критика из EvidenceLink исключаются. Условия v1.5.2 передаются только как нейтральные ограничения launch_context или отдельные проверяемые тезисы с предпосылками; полный объект eligibility, вердикт о допуске и объяснение исследователя в handoff не добавляются.

До вызова Verifier выполняются schema/ID/scope-проверки и отдельная проверка нейтральности: ограниченный служебный LLM-вызов получает только текст тезиса и рубрику «нет вердикта, уверенности, приоритета, команд». Он возвращает accept/reject/uncertain с краткой причиной, не переписывает тезис. reject/uncertain дают одну попытку исправления критиком ДО проверки, затем needs_review. Проверяющему не передаётся результат этой служебной проверки. Это снижение риска, не гарантия отсутствия смыслового влияния; инструменты не исполняют команды из строк. Вызов учитывается в бюджете и версии промптов.

Запрещены: impact, confidence, why_it_matters, likelihood_note, critic_summary, critic_order, rank, score, выводы других моделей, история чата критика. Ссылки могут содержать позицию автора источника — это допустимое доказательство, не гарантия полной слепоты. Мнение критика не добавляется в поисковый запрос проверяющего.

## Второй агент: Verifier

Для каждого переданного тезиса читает предложенные источники, проверяет соответствие цитаты и контекста, ищет опровержения/независимое подтверждение при недостаточности. Выход: Verification[] + новые Claim/Evidence/Conflict. Статусы: supported/refuted/mixed/insufficient/not_fact_checkable. Прогноз не объявляется истинным фактом: проверяются его предпосылки. Не оценивает привлекательность бизнеса и не формирует рейтинг. Лимит: до 6 поисковых запросов и 10 новых чтений на модель; если локальной квоты не хватает для обязательных тезисов — technical_incomplete, при общем лимите run/study — paused по 10-operations.

## Изоляция и аудит

- Каждая роль и модель получают новый контекст; общего conversation/thread ID и общей изменяемой памяти нет.
- Инструменты агента не имеют произвольного SQL/доступа к файловой системе. Они читают только переданный пакет и разрешённые source IDs/URL.
- Можно использовать одного провайдера для обоих агентов; это не называется статистической независимостью. Разные модели не заменяют изоляцию.
- Полный очищенный вход роли, промпт с версией, вызовы инструментов и публичное обоснование ответа сохраняются. Не требовать и не логировать скрытую цепочку рассуждений провайдера.
- Автоматическая проверка handoff по разрешённой схеме выполняется до вызова Verifier. Хеш сам по себе не доказывает изоляцию — для ревью нужен сам очищенный payload и журнал доступа.
- Результат Verifier попадает в reconciliation, никогда обратно в Critic.

## После проверки

Reconciliation — детерминированная стадия, вход Risk/Claim/Verification текущей ревизии, выход RiskAssessment и затронутые criterion/factor IDs. Для каждого риска: refuted хотя бы у essential premise → refuted_basis; иначе неполная/mixed/insufficient обязательная предпосылка → unresolved; иначе все существенные фактические предпосылки supported → supported_basis. Непроверенные вспомогательные тезисы остаются видимыми; если они нужны выводу о риске, результат unresolved. Для прогноза без проверяемых предпосылок результат unresolved. supported_basis подтверждает фактическую основу, а не истинность прогноза; refuted_basis отвергает текущий аргумент, не доказывает отсутствие риска вообще.

Исходные ответы сохраняются. Опровергнутый аргумент не используется как факт для снижения балла. P05 оценивает последствия по проверенным предпосылкам и явно указанным условиям сценария; общий балл считает код. Незавершённая обязательная проверка при доступных числовых основаниях даёт provisional, а отсутствие обоснованного фактора/диапазона — unavailable по 07/15. Завершённое исследование с открытым разрешённым условием F01/F03/F05–F07 допускает conditional, если значения/диапазоны всех пяти факторов обоснованы; такая неизвестность сама по себе не повод пропускать Critic/Verifier или изображать проверку завершённой. При обнаружении новых фактов, затрагивающих критерий, стадия направляет его на повторную независимую проверку правил 04/15 и пересчёт eligibility.

## Уточнение единицы анализа v0.3

Вход каждой роли содержит assessment_scope_id, базовую модель, выбранный вариант, рынок и сценарий ресурсов. Критик анализирует риски этого варианта, проверяющий проверяет тезисы в том же scope. Handoff допускает base_model_id/variant_id/assessment_scope_id и описания варианта как нейтральный контекст, но не оценки других вариантов. Служебная классификация определяет primary_group, теги и гипотезы объединения; не ранжирует и не выбирает победителей. Разные компании-примеры одного варианта не запускают независимый дубль оценивания.

Для политики v1.5.2 наличие аналога, покупателей и публикаций помогает выбрать рынок-кандидат, но не доказывает законность ни в этом рынке, ни «где-нибудь». Лицензия аналога/партнёра не освобождает нашу роль автоматически. Другой рынок требует отдельного явно заданного launch_context/scope и нового прохода критериев и факторов; роли не меняют рынок внутри текущего вызова. Старый результат сохраняется, его score не переносится в новый рынок.

## Выполнение через LangGraph, baseline v1.1

Research/filter, Critic, handoff+neutrality gate, Verifier, reconciliation, factors и card validation — явно именованные узлы/подграфы с отдельными Pydantic-контрактами. Переходы задаются кодом графа по валидированным результатам, не свободным решением LLM. Не более двух assessment scopes выполняются параллельно. LangGraph не заменяет проверки evidence, критериев, рейтинга и бюджета.

Для v1.5.2 research включает проверяемое завершение AnalogueLegalReview, а card validation сверяет полноту reviews с manifest аналогов. Final/conditional требуют completed для каждого используемого аналога, но не требуют coverage=reviewed: completed not_found/unavailable/insufficient допустимы при сохранённых пробелах и выполнении политики критериев/факторов. Отсутствующий review не заменяется записью not_found.

Изоляция обеспечивается явным построением входного пакета для каждого модельного вызова. Узел Verifier не сериализует весь GraphState, checkpoint, историю сообщений, исключение или trace в запрос: только whitelist из раздела handoff. Новый вызов не получает previous_response_id/conversation критика. Состояние графа может ссылаться на оба отчёта для reconciliation, но агентам эти ссылки не открывают общий инструмент чтения. LangGraph thread_id не передаётся как conversation ID OpenAI. Тестировать фактические инструкции, вход, tool arguments/results проверяющего, а не только тип состояния.

Ручная проверка использует interrupt с отдельным question/revision ID и продолжение через Command(resume=...). Узел с interrupt может выполняться заново с начала: платные запросы и запись аналитического результата должны находиться в отдельных идемпотентных шагах с квитанциями. Решение владельца валидируется до resume. После изменения допуска на confirmed или conditional граф проходит все отсутствующие Critic/Verifier и последующие проверки; само ручное решение их не заменяет. Изменение уже использованного critic input требует нового run по 04/15. Ответ Verifier обратно критику не передаётся.
