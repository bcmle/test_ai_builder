## Правила Spec-Driven Development

- Локальный `full_tt.md` хранит исходные требования, изменения и историю обсуждения и не публикуется. Этот публичный комплект детализирует предлагаемое поведение и содержит сведения, необходимые для ревью.
- Пока статус DRAFT, предложения можно менять. Требования исходного задания и явные решения пользователя нельзя молча ослаблять. Конфликт документации — повод исправить спеки до реализации.
- Порядок изменения: требование/допущение → затронутые контракты и критерии приёмки → ревью пользователя → новая версия → реализация.
- После согласования сохранить версию baseline в Git. Каждый этап реализации ссылается на requirement ID и acceptance ID.
- Заменив допущение, проверить связанные промпты, конфигурацию, рейтинг и тестовые сценарии. Старые прогоны сохраняют старые версии, а не меняются задним числом.
- Runtime JSON Schema, конфиги, миграции и тесты будут кодом реализации. Сейчас описаны их контракты в Markdown; исполняемых файлов проекта нет.
- Конкретные model ID, тарифные лимиты, ключи и параметры сервера требуют проверки перед интеграцией. Текущий комплект не утверждает, что доступы уже существуют.

## Границы готовности документа

Описаны контракты и целевое поведение всех этапов. Не проведены живой прогон, измерение качества LLM, проверка доступов и развёртывание. Любые оценки стоимости и ресурсов — плановые ограничения, не измеренные факты. Конкретные UI-макеты и финальный провайдер уточняются при ревью.
