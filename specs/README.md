# Спецификации конвейера проверки бизнес-моделей

Версия: 1.5.2. Дата: 16.11.2026. Статус: спецификации v1.5.2 согласованы; пользователь разрешил реализацию и поочерёдное обновление существующей подборки.

## Текущий шаг v1.5.2: юридические документы аналогов и условный score

Для каждого основного и дополнительного аналога требуется поиск и изучение доступных релевантных Terms и других юридических документов. Сохраняются источники, пункты, даты/версии, договорные роли, применимость к нашей модели и пробелы. Завершённость обзора отделена от наличия/достаточности документов: выполненный ограниченный поиск с not_found/unavailable/insufficient сохраняет возможность conditional score по остальным правилам допуска. Пропущенный обзор не объявляется завершённым; найденные Terms не дают автоматического юридического pass. Подробный процесс — 02/15, данные/роли — 03/05/06/08, отображение — 09, приёмка — S16–S20, решение — D13.

По просьбе пользователя разделены ограничения самой модели и проверки перед запуском. F05–F07 остаются ограничениями выбранной конструкции без нашего кредитного/страхового риска и хранения чужих денег; их неполное внешнее подтверждение не блокирует условную оценку автоматически. Незавершённая подробная проверка F01/F03 после предварительного исследования может стать явным условием допуска: F03 unknown больше не блокирует conditional score сам по себе. Подтверждённый применимый запрет или обязательная собственная специальная лицензия до первого клиента исключают выбранный сценарий; существенное нерешённое противоречие остаётся unresolved. F09 исключает официальный государственный сервис, а не частный продукт с государственным заказчиком. F02/F04/F08/F09/F10 требуют pass; веса и требования доказательности факторов сохраняются.

Публичный аналог с покупателями не доказывает законность или ненужность нашей лицензии. Другой рынок требует явно нового сценария и оценки критериев/факторов, без переноса прежнего score. Эти уточнения v1.5.1 заменяют первоначальное правило проекта v1.5 о блокировании score при F03 unknown и не меняют исторические анализы; решение записано как D12 в 12-decisions.

Приоритетный контракт — [15-conditional-scoring.md](15-conditional-scoring.md). Вводятся отдельные confirmed/conditional допуски и final/conditional рейтинги; обе оценки требуют полного Critic/Verifier и проверки карточки. Неизвестность и условия видны, старые snapshots и оплаченные ответы не переписываются. Изменены связанные данные, промпты, маршруты стадий, UI и приёмка S01–S20 на уровне требований. Новое поручение разрешает реализацию, выпуск и переоценку в прежнем общем бюджете. Очередь: сначала F10=pass, затем минимум unknown; публикация после каждой карточки. Подробнее — раздел о поочерёдной переоценке в 15 и решение D14.

## Текущий результат v1.3: минимальный красивый прототип

Пользователь утвердил сокращённый план реализации: публичный сайт только для чтения с **20 различными бизнес-моделями до фильтрации**, объяснениями всех отказов/неопределённостей, стандартными карточками прошедших и рейтингом. Исходное задание CEO требовало 10–15 моделей; расширение до 20 — явное решение пользователя, не требование 20 успешных карточек. Состав фиксируется до обязательных фильтров, число прошедших не гарантируется. Неполный набор (<20) маркируется как неполный.

Приоритет: приятный английский интерфейс → последовательный ручной серверный сбор подборки → опубликованный безопасный JSON-снимок → выпуск существующим GitHub Actions на Aeza. Сравнение до трёх моделей одного сценария; фиксированный сценарий США, два человека, $15 000 без зарплат, 90 дней. Все расходы поиска и анализа входят в общий бюджет подборки, учёт не сбрасывается между моделями. Повторная сверка тарифов не является задачей этого этапа.

Первоначальный доступ v1.3 — HTTP по IP; дополнение v1.3.1 переводит адрес демонстрации на доменный HTTPS, без логина и действий, запускающих расходы. Owner UI, постоянный worker, многоцикловое исследование рынков, полный каталог, сложные ручные ревизии и подробный экран расходов отложены. Существующие PostgreSQL, LangGraph, журнал расходов, секреты и защищённое хранение доказательств сохраняются. Ни одно упрощение не отменяет обязательный gate, изоляцию Critic/Verifier и паспорта утверждений.

Разделы v1.3/v1.3.1/v1.4 описывают предыдущие поставки и их frozen-контракты; текущий шаг требований — v1.5.2. Расширенные контракты после прототипа не становятся блокирующей приёмкой только из-за смены номера версии. Конкретные шаги и приёмка — [11-acceptance.md](11-acceptance.md). Неизменённые контракты остальных документов продолжают действовать; новая политика 15 заменяет прежний запрет любого score при unknown только в указанном объёме.

## Правила Spec-Driven Development

- Локальный `full_tt.md` хранит исходные требования, изменения и историю обсуждения и не публикуется. Этот публичный комплект детализирует предлагаемое поведение и содержит сведения, необходимые для ревью.
- Пока статус DRAFT, предложения можно менять. Требования исходного задания и явные решения пользователя нельзя молча ослаблять. Конфликт документации — повод исправить спеки до реализации.
- Порядок изменения: требование/допущение → затронутые контракты и критерии приёмки → ревью пользователя → новая версия → реализация.
- После согласования сохранить версию baseline в Git. Каждый этап реализации ссылается на requirement ID и acceptance ID.
- Заменив допущение, проверить связанные промпты, конфигурацию, рейтинг и тестовые сценарии. Старые прогоны сохраняют старые версии, а не меняются задним числом.
- Спеки определяют целевые контракты; степень реализации отражается отдельно в docs/implementation.md. Утверждение спецификации не означает прохождения её тестов.
- Выбраны gpt-6-astra, Tavily и Aeza SWEs-2; доступы подтверждены. Тарифные версии фиксируются при интеграции, секреты не публикуются.

## Границы готовности документа

v1.5.2 сейчас существует только как спецификация. Приёмка S01–S20 задаёт будущие проверки реализации, не свидетельствует об их прохождении. Согласование менее жёсткого допуска не гарантирует score каждой модели: применимый запрет/обязательная собственная специальная лицензия, нерешённое существенное противоречие, unknown неизменённых gates, отсутствие обоснованного S-фактора или незавершённые обязательные стадии по-прежнему препятствуют рейтингу. Сама по себе незавершённость подробной проверки F01/F03 больше не является таким препятствием при соблюдении контракта 15.

Baseline v1.3 утверждён пользователем для реализации. PostgreSQL/LangGraph, технический выпуск и получение реальных источников уже реализованы и развёрнуты на Aeza. Первый live scope с аналогом Calendly завершился needs_review: 6 критериев pass, F01/F03/F05/F07 unknown; Critic/Verifier не запускались, финального рейтинга нет. Это реальный результат фильтрации, а не подтверждённый полный путь до рейтинга. Исторические формулировки «предлагается/на ревью» описывают прошлые итерации; актуальный статус задан этим baseline и 12-decisions. Утверждение спеков не означает готовности прототипа.
