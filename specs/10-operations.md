# 10. Сбои, лимиты, безопасность и размещение

Статус: APPROVED BASELINE v1.1 (пользователь, 15.11.2026). Числа ниже — начальные настройки на ревью.

## Бюджет выполнения

target_models=12; concurrent_models=2; max_active_runs=1; llm_timeout=120s; run_wall_time=45min; max_provider_requests=180; max_search_requests=120; max_document_fetches=180; max_run_cost_usd=25. Время/деньги — пределы, не гарантированная стоимость или обещание уложиться. 90 дней относятся к запуску бизнеса, не длительности анализа.

Локальные квоты: discovery до 12 поисковых запросов за цикл; накопительная цель 40 кандидатов, cap 50 по конфигурации 13-catalog; research до 4 запросов/6 новых чтений на модель; critic до 3/5; verifier до 6/10. Они являются максимумами, не квотами, которые необходимо израсходовать; общий лимит может остановить раньше. Существенные конфликты используют оставшийся общий бюджет, не получают неограниченные дополнительные вызовы.

Перед каждым внешним платным запросом резервировать верхнюю оценку расхода по тарифной конфигурации, лимиту выходных токенов и измеренному/консервативно оценённому входу. Если верхнюю оценку определить нельзя, live run не стартует до настройки лимитов. Сохранить BudgetReservation из 03-data до отправки запроса. Один request_id обозначает одну физическую попытку отправки; transport retry имеет новый request_id и новый резерв, а общий logical_request_id связывает эти попытки в журнале.

Проверка доступного остатка, увеличение счётчика запросов и создание резерва выполняются одной транзакцией для обоих уровней — run и MarketStudy; discovery без run резервирует только study. Учтённый расход равен сумме actual_amount для settled и amount_upper для reserved/unknown; released даёт ноль. Все суммы сравниваются в валюте бюджета по зафиксированной тарифной политике. Два параллельных исполнителя не могут зарезервировать один остаток. Счётчик физических попыток не уменьшается при освобождении денежного резерва.

После ответа с известным usage резерв становится settled с actual_amount; неиспользованный остаток высвобождается. После достоверно не отправленного или документированно неоплачиваемого запроса резерв становится released. Таймаут после возможной отправки, разрыв соединения и crash до сохранения usage переводят резерв в unknown: вся верхняя сумма остаётся занятой после restart/resume. Освобождение unknown возможно только по результату сверки с провайдером или документированному решению владельца с основанием об отсутствии списания; простое нажатие resume резерв не снимает. Повторная обработка того же request_id не создаёт второй резерв и не удваивает settlement. Поздний usage уточняет только собственный резерв и расход, а не устаревший результат аналитического этапа.

Вести actual/estimated/unknown отдельно. API billing может запаздывать, hard cap — локальный предел запуска новых запросов, не гарантия итогового счёта. Если actual неожиданно превысил зарезервированное, записать фактический расход и нарушение оценки тарифа, приостановить новые платные вызовы до решения владельца. При нехватке остатка для следующего резерва — paused с причиной и сохранёнными результатами. Изменение лимита владельцем фиксируется отдельной ревизией политики исполнения и событием; аналитический scenario/критерии/промпты не меняются и завершённые этапы не инвалидируются только из-за продления бюджета. Автоматического превышения нет.

`run_wall_time=45min` означает накопленное время работы run в состоянии running, включая сетевые ожидания, backoff и паузу circuit breaker, но исключая явное состояние paused. Параллельные задачи не суммируют одно и то же время дважды. Хранить накопленное активное время и начало текущего активного интервала; после crash закрыть незавершённый интервал не позже истечения последнего действующего worker lease, консервативно учитывая время до обнаружения остановки. Resume продолжает остаток, не обнуляет время/деньги/запросы. При исчерпанных 45 минутах возобновление требует явного продления владельцем с записью события и новой ревизией политики исполнения. Внешний вызов не стартует без оставшегося времени; его timeout ограничивается остатком активного времени и лимитом конкретного адаптера. При остановке run результаты и резервы сохраняются.

## Повторы и восстановление

Различать stage_execution_id (выполнение роли), iteration_id (шаг tool loop), logical_request_id (один запрос модели/инструмента) и request_id (физическая попытка). Успешный следующий шаг tool loop не является повторной попыткой предыдущего. StageExecution.request_count считает все физические вызовы LLM этой стадии, включая transport retries и schema repair; StageExecution.attempt_count считает запуски/восстановления самой стадии и не сбрасывает request_count. Поисковые запросы и чтения имеют собственные счётчики, все относятся к run/study.

Временные сетевые ошибки, таймаут, rate limit и 5xx: для одного logical_request_id исходная попытка плюс максимум две дополнительные. Задержка min(30s, 2s×2^(attempt-1)) плюс случайная добавка 0..1s; Retry-After имеет приоритет, если укладывается в оставшееся активное время run. Если нет — paused. Каждая новая попытка предварительно резервируется и учитывается в общем бюджете. Автоповторы SDK отключить либо включить в этот же счётчик; вложенное умножение запрещено. Сбой позднего запроса не повторяет ранее успешно сохранённые шаги роли или инструмента.

401/403, invalid request и исчерпанная квота/баланс не повторяются автоматически. Общая проблема credentials приостанавливает весь run; локальная ошибка документа не блокирует остальные модели. Для невалидного финального структурированного результата роли допускается один schema-repair запрос с ошибками валидации; это отдельный logical_request_id с тем же ограниченным transport retry, а не перезапуск всей роли. Повторный невалидный результат даёт technical_incomplete. Отказ модели и контекстный лимит — отдельные причины, не пустой successful result.

Tool loop ограничен счётчиками запросов, инструментов, денег и активного времени. `max_stage_provider_requests` задаётся в конфигурации роли и не может превышать `max_provider_requests`; если отдельный потолок не задан, он равен существующему общему потолку 180, а остаток run/study всё равно имеет приоритет. Каждый физический LLM-вызов, в том числе успешный, уменьшает доступный остаток. Поэтому новая итерация или schema repair не открывают новый бюджет. Если очередь роли требует следующий вызов сверх локального потолка, стадия становится technical_incomplete; при общем лимите run/study — paused. Ни одно из этих состояний не является бизнес-отказом модели.

После трёх последовательных временных ошибок одного провайдера приостановить новые запросы к нему на 60 секунд. Уже завершённые результаты сохранить; после паузы один пробный вызов в рамках бюджета. Веб-интерфейс остаётся доступен. Резервного провайдера в v1 нет.

Worker захватывает RunLease, а не StageExecution-очередь. Каждый завершённый узел фиксирует результат/квитанцию в application DB и затем checkpoint LangGraph до перехода дальше. Новый владелец истёкшей аренды продолжает граф с checkpoint и сверяет квитанции; предыдущий token не может продлить аренду, записать результат или checkpoint. Перед каждой физической попыткой проверяются lease, остаток времени, лимиты запросов и бюджет.

Запись результата, StageExecution receipt и аудита атомарна в application DB и защищена RunLease token. Следующий узел выбирает LangGraph, не приложение через next_stage. Checkpoint DB фиксируется отдельно; разрыв обрабатывается по 08-architecture. Поздний ответ старого worker не меняет активный результат/очередь/граф; допускается идемпотентное уточнение его собственного usage/reservation. При утрате lease прекращаются новые tool calls. Уже отправленный вызов может быть оплачен; exactly-once billing не обещаем. Квитанции и сохранённые tool results переиспользуются только при совпадении scope/input/config/prompt/iteration ключей.

## Логи

run/model/stage/attempt IDs, timestamp, config/prompt versions, provider/model, duration, tokens/cost при наличии, категория ошибки, источники, переданные агенту данные, результаты валидации и изменения статусов. Пароли, API keys, cookies, Authorization, приватные сетевые реквизиты не логируются. Публичная проекция показывает нужные для проверки независимости payload без секретов и больших исходных статей; полные snapshots — только владельцу.

## Публичный сайт

Один владелец; пароль хранится в виде стойкого хеша, сессия в HttpOnly/Secure/SameSite cookie. Rate limiting входа; CSRF на мутации; гостевой write всегда запрещён. Текст LLM/источников экранируется, HTML источника не рендерится. Экспорты генерируются из разрешённой схемы, не прямым дампом БД. Произвольные команды, URL endpoints провайдера и файловые пути из входов пользователя/агента не выполняются. Защита fetch описана в 02-sources.

## Aeza и GitHub

Размещение: Aeza SWEs-2, Стокгольм, Ubuntu 24.04, 2 vCPU/4 GB RAM/60 GB NVMe. Astra и Tavily вызываются внешними API; Mac не нужен для выполнения развёрнутого приложения. Доступы API проверены, нагрузочные измерения приложения ещё не проведены. Домен и стабильный доступ для деплоя готовятся до публичного размещения.

До интеграции проверить доступность выбранных LLM/search API из выбранного региона сервера и допустимость использования аккаунта; не обходить региональные ограничения. Если API недоступен, пересмотреть регион или провайдера через изменение спеки.

Публичный GitHub содержит код, спеки, примеры конфигурации без секретов, небольшие синтетические fixtures и инструкции. Не коммитить .env, рабочую БД, полные web snapshots, private logs, секреты или частные данные. Изучить исходный текст тестового на допустимость публикации; если разрешение на его публикацию неясно, не включать оригинал и переписку CEO в публичный репозиторий, оставить собственную спецификацию/описание задачи.

Docker Compose: reverse proxy + web + worker, persistent volume для DB/snapshots. TLS обязателен. Подключённые к БД процессы запускаются от непривилегированного пользователя. Backup включает согласованные SQLite backups application DB и LangGraph checkpoint DB, все immutable evidence/snapshot/audit-payload файлы, на которые ссылается этот снимок БД, и manifest с относительными путями, размерами, hashes, версией схемы и сохранёнными конфигами/промптами. Не копировать активный db-файл без WAL как полноценную резервную копию.

Для одного сервера процедура проста: приостановить команды и изменения через web, дождаться завершения текущего вызова либо ограниченного таймаута и остановить граф на сохранённой границе; убедиться, что worker больше не пишет, сделать SQLite backup обеих баз, скопировать достижимые immutable файлы и проверить manifest, затем разрешить работу. Секреты в публикуемый manifest не включаются; доступ к приватным резервным копиям только у владельца. Для rollback сохранить соответствующий release приложения и инструкции восстановления; старые файлы доказательств не перезаписываются новой версией.

Backup обязателен перед обновлением/миграцией; до сдачи restore проверяется в отдельном каталоге: запуск приложения, открытие опубликованной карточки, её evidence snapshot и audit payload, чтение replay-данных и сверка hashes. Одного health endpoint недостаточно. Run history не удаляется автоматически в v1; при нехватке диска новый run блокируется, активная работа останавливается с сохранением последнего целого состояния насколько позволяет диск. Миграции/rollback фиксируются в release-инструкции.

## Дополнение v0.2: бюджет исследования рынка

Per-run лимиты сохраняются. MarketStudy дополнительно имеет явный суммарный бюджет и счётчики запросов всех дочерних run/discovery cycles. До задания owner лимита первый live study не запускается; бюджет не выводится из числа стран. Исчерпание означает паузу и незавершённое покрытие, а не сигнал переходить к следующему рынку. Состояние очереди стран сохраняется при перезапуске.

Расширение discovery до ориентира 30–50 кандидатов не увеличивает автоматически лимит глубоких проверок: они выполняются для фиксированной подборки 10–15 моделей. Расход discovery-циклов суммируется в MarketStudy; после лимита — пауза без обхода новым run. Количество кандидатов не гарантируется доступным бюджетом.

## Учёт расходов, согласовано 15.11.2026

Лимит $25/run включает все внешние API этого запуска: LLM, поиск, извлечение, retries, schema repair и служебные проверки. Это потолок, не целевой расход. Бесплатные кредиты не делают потребление нулевым: для контроля лимита считаем стоимость по сохранённому тарифу, фактическое денежное списание показываем отдельно, если оно известно. Стоимость VPS/домена не включается в API/run; их расходы хранятся отдельно как инфраструктурные, при наличии введённых владельцем данных.

До discovery создаётся run со статусом selecting и бюджетным scope; discovery подготовки этой подборки относится к нему и входит в $25. Study-only discovery требует отдельного явного лимита владельца и не используется для обхода run cap. Переиспользование существующего источника не списывает расход второй раз. $25/run не означает бесконечные автоматические запуски: study имеет самостоятельный явный лимит, новые исследования запускает владелец. Общий бюджет всех будущих исследований не предполагается из согласования per-run.

Для каждой физической попытки сохранять UsageRecord: request_id/provider_request_id, logical_request_id, study_id/run_id, assessment_scope_id nullable, stage/agent, provider/model/endpoint, purpose (development/eval/live), timestamps/duration/status/error_kind, retry_of nullable, input_tokens/output_tokens/cached_input_tokens/reasoning_tokens nullable, search/extract credits и billable units, pricing_version, currency, estimated_cost_usd, calculated_cost_usd nullable, billed_cost_usd nullable, cost_status estimated/reported_usage/reconciled/unknown, reservation_id и исходный usage payload без секретов. Неизвестный usage — null, не ноль. Reasoning/cached tokens могут быть подмножествами output/input: правила провайдера определяют расчёт без двойного счёта. Версию тарифа сохранять с единицами, датой и источником; расходы считать decimal, округлять только при показе.

UsageRecord отражает одну физическую попытку; позднее уточнение создаёт корректирующее событие, а не второй расход. Провайдерский usage позволяет рассчитать стоимость, но не доказывает фактическое списание по счёту. Остаток лимита = 25 минус settled consumption и reserved/unknown; резервы не складываются повторно с тем же settled usage. Если верхняя оценка очередного вызова превышает остаток, вызов не отправляется. Resume сохраняет расход, продление лимита требует явного действия владельца с записью старого/нового значения и причины.

Сводки: весь проект, study, run, модель/вариант, роль/этап, провайдер, дата и purpose. Показать токены, кредиты, рассчитанную стоимость, подтверждённые списания, неопределённый расход, резерв, остаток; долю retries/ошибок и стоимость на исследованную/допущенную/полностью оценённую модель. При нулевом знаменателе — N/A. Исторические значения не пересчитываются молча по новому тарифу. Прогнозы будущего расхода основаны на наблюдавшихся прогонах и показывают размер выборки, не гарантированный бюджет.

## Resume, retries и checkpoint replay v1.1

Transport retries принадлежат metered adapters: исходный вызов + максимум два повтора. Автоматические node retries LangGraph для платных узлов отключены, чтобы не умножать попытки. Один schema repair и успешные шаги tool loop имеют собственные квитанции и общий бюджет роли/run/study. BudgetReservation/UsageRecord живут вне GraphState и не откатываются при checkpoint replay/time travel. Повтор API после crash с неизвестным результатом сначала ставит run на техническую паузу; возобновление с явно зарегистрированным разрешением повторить создаёт новый request_id, сохраняя старый unknown reserve и лимит.

Ручной interrupt исключается из активного времени после перехода run в paused; backoff/circuit breaker во время running учитываются. Решение одного manual question не снимает другие вопросы и общую бюджетную паузу. Продление лимита не изменяет аналитический input hash и не запускает завершённые узлы заново. LangGraph trace/checkpoint не является разрешением публиковать полный state: наружу идёт только очищенный application audit. Секреты в checkpoints не сохраняются; ключи передаются адаптерам из runtime окружения.

Backup manifest содержит обе схемы БД, graph_version/state_schema_version и версии библиотек. Restore проверяет чтение evidence/usage и продолжение прерванного графа без повторного платного вызова для уже сохранённой квитанции. Rollback приложения возможен только при совместимости с checkpoint и domain schemas; иначе требуется восстановление согласованного backup или явная миграция.
